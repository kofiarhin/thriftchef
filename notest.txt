OBSOLETE — kept for history only. Do not treat as requirements.

This file recorded problems with an earlier build of ThriftChef, from before
the planner was rewritten. Every item in it describes behaviour the code no
longer has, and reading it as a to-do list would send someone chasing bugs that
cannot occur.

What changed, item by item:

1. "Have to retry more than once before the plan is generated."
   Generation is no longer a network call to a model. It is a bounded local
   search that either returns a plan or a typed, actionable error. There is
   nothing to retry into success.

2. "Generation is slow"; "want to run the request through the NVIDIA API".
   There is no external API in the request path and no model of any kind. The
   deterministic engine finishes a week in tens of milliseconds against an
   80-product selection, with a hard 1.5-second ceiling. See
   `server/testing/baseline/BENCHMARK.md` for measured figures.

3. "UI design is trash. Need to redesign the UI."
   The client has been rebuilt around a router with dedicated onboarding, plan,
   recipe and shopping screens.

4. "Optimize the use of images; layout is too text-centred."
   Still open as a design concern, and not tracked here. Raise it as its own
   issue if it matters.

5. "At least breakfast/lunch/dinner should be selected; error feedback if the
   user selects none."
   `mealsPerDay` is required by request validation and the form reports the
   problem against the control. Covered by tests in
   `server/mealPlanning/mealPlanSchemas.test.ts`.

6. "Plan generation timed out. The meal plan service did not finish within two
   minutes."
   That error message no longer exists. The two-minute service timeout belonged
   to the removed model call; the planner's own ceiling is 1.5 seconds and its
   failure is reported as `PLANNER_CAPACITY_EXCEEDED`.

This file is retained rather than deleted because removing project notes was
not within the approved scope. It carries no outstanding requirements.
